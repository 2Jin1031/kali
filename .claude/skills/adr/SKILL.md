# /adr — ADR 제안 초안

결정할 질문: $ARGUMENTS

## 규칙

- 상태는 항상 `제안`. `수락됨`으로 쓰지 않는다. 고르지 않는다 (추천은 쓰되 결정 칸은 비워 둔다)
- 수락된 ADR은 고치지 않는다. 반대하면 새 ADR을 만들고 "대체 제안: 000N"으로 가리킨다
- 선택지는 2~3개. 실제로 고를 만한 것만. "아무것도 안 함"이 현실적이면 그것도 선택지
- 사실(버전, 지원 기간, 기능 유무)은 확인한 것만 쓰고 출처와 확인 날짜를 적는다. 확인 못 했으면 "확인 못 함"
- 계획·브레인스토밍은 쓰지 않는다. 결정에 필요한 것만

## 절차

1. `docs/adr/`의 기존 ADR을 읽어 관련 결정과 충돌하는지 본다
2. 다음 번호를 정한다 (가장 큰 번호 + 1, 4자리)
3. `docs/adr/NNNN-영문-하이픈-제목.md` 를 아래 형식으로 만든다
4. `docs/adr/README.md` 목록에 한 줄 추가 (상태: 제안)
5. 사용자에게 추천과 그 이유를 세 줄 이내로 말하고, 수락 여부를 묻는다. 대화형이 아니면 PR "내가 결정할 것"에 적는다

## 형식

```markdown
# NNNN. 제목

상태: 제안
날짜: YYYY-MM-DD
(대체 제안: 000N — 해당할 때만)

## 상황

왜 지금 정해야 하나. 제약, 관련 ADR, 확인한 사실(출처·날짜).

## 선택지

- (가) ...
- (나) ...
- (다) ...

| 기준 | (가) | (나) | (다) |
|---|---|---|---|
| ... | ○ / △ / ✕ + 짧은 이유 | | |
| 나중에 바꾸는 비용 | | | |

추천: (가). 이유 한두 줄.

## 결정

(사람이 수락할 때 채운다)

## 결과

고르면 무엇이 바뀌나 (추천 선택지 기준). 보호 경로 변경이 필요하면 적는다.

## 재검토 조건

어떤 일이 생기면 다시 볼지 (관측 가능한 조건으로).
```
