# 도메인 스펙

엔티티·스키마와 기능을 만들 때 따르는 기준이다. 나중에 바꾸면 데이터 마이그레이션이 필요한 것만 정한다.
API URL, 응답 필드, UI, 캐시 키, MQ 토픽 이름처럼 코드만 고치면 되는 것은 정하지 않는다.

- 위치와 보호: [ADR 0010](../adr/0010-domain-spec-location.md). AI는 이 문서를 고치지 않는다. 바꿔야 하면 PR "내가 결정할 것"에 적는다
- 여기 없는 도메인 규칙이 필요하면 묻는다. 묻지 못하면 PR "내가 결정할 것"에 적는다
- "미정"은 아직 정하지 않은 것이다. 미정인 부분은 추측해서 구현하지 않는다
- 깊이: P0 기능은 유스케이스와 규칙까지, P1·P2는 데이터에 생기는 일과 받게 될 이벤트만

| 순서 | 기능 |
|---|---|
| P0 | 홈 한 줄 소개, 최근 글·글 목록·글 상세(태그 표시), 본문 링크로 다른 글 이동, 홈 히스토리 잔디(코테, 영어) |
| P1 | 대표 글, 글 끝 "이 글을 언급한 글", 링크에 마우스 올리면 요약, 안 하기 히스토리와 히스토리 페이지 |
| P2 | 글 속 동작 데모, 태그 페이지·필터, 검색 |

## 1. 원본 위치

- 글의 원본은 옵시디언이다. DB는 동기화로 채우는 사본이다
- 글은 옵시디언에서만 쓰고 고친다. 블로그에는 글 편집 화면이 없다
- 동기화는 옵시디언의 내용으로 DB를 덮어쓴다. DB에서 직접 고친 내용은 다음 동기화 때 사라진다
- 히스토리의 원본: 9. 히스토리

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 글 | 옵시디언에서 발행한 문서 하나 |
| 개념 글 | 다른 글 속 개념을 설명하는 글 (예: "윈셋"). 데이터에서는 일반 글과 같은 글이다. 구분이 필요하면 태그로 한다 |
| 링크 | 글 본문에서 다른 글이나 외부 URL로 가는 연결. 글을 쓸 때는 내 글로 연결할 수 있으면 내 글로, 없으면 외부 링크로 잇는다 |
| 히스토리 | 날짜별로 쌓이는 활동 기록. 코테, 영어, 안 하기 세 종류 |
| 스트릭 | 안 하기 항목을 지킨 연속 일수 (예: "사과게임 안 한 지 47일") |
| 태그 | 글에 다는 이름. 글 하나에 여러 개를 단다. 카테고리는 없다 |
| 대표 글 | 홈의 "여기부터 보세요"에 순서대로 나오는 글 |
| 요약 | 글을 한두 문장으로 줄인 것. 링크 미리보기, 글 목록, 공유 미리보기에 쓴다 |

- 화면과 문서에서는 "로그" 대신 "히스토리"라고 쓴다
- 히스토리의 코드·테이블 이름: 미정 (엔티티 단계에서 정한다)

## 3. 글 식별

- 같은 글인지는 frontmatter의 `id`로 판단한다. 파일 이름이나 폴더가 바뀌어도 `id`가 같으면 같은 글이다
- `id`는 한 번 정하면 바꾸지 않는다
- 파일 경로(`sourcePath`)는 식별자가 아니다. 어느 파일에서 왔는지 기록하는 용도다
- `id` 형식은 UUID다. 옵시디언 템플릿이 새 노트를 만들 때 넣는다
- URL의 slug는 frontmatter의 `slug`로 받는다. 제목에서 만들지 않는다. 형식은 영문 소문자, 숫자, 하이픈
- slug가 바뀌면 옛 slug를 보관하고, 옛 URL은 새 URL로 리다이렉트한다
- slug는 모든 글에서 유일하다. 다른 글이 지금 쓰거나 예전에 쓴 slug는 쓸 수 없다 (옛 링크가 다른 글로 가지 않게)

## 4. 글 상태

```
(옵시디언에만 있음) --발행--> PUBLISHED --발행 취소--> UNPUBLISHED
                                  ^                        |
                                  +-------다시 발행---------+
```

- DB의 글 상태는 `PUBLISHED`, `UNPUBLISHED` 두 가지다. 초안은 옵시디언에만 있고 DB에 들어오지 않는다
- 발행을 취소해도 행을 지우지 않는다. id, 처음 발행일, 옛 slug 기록이 남는다
- `UNPUBLISHED` 글은 화면에 보이지 않는다
- `UNPUBLISHED` 글이 다시 발행되면 같은 글로 돌아온다. 처음 발행일은 그대로다

## 5. 발행 (동기화)

동기화는 옵시디언 볼트를 읽어 DB의 글을 맞추는 동작이다. 발행, 다시 발행(수정), 발행 취소가 모두 동기화 한 번 안에서 일어난다.

### 발행 대상

- frontmatter에 `publish: true`가 있는 노트만 발행 대상이다. 폴더 위치는 상관없다
- DB에 있던 글이 이번 발행 대상에 없으면 `UNPUBLISHED`가 된다 (`publish`를 지우거나 false로 바꾸거나 파일을 지운 경우)
- 동기화가 찾은 발행 대상이 0개면 아무것도 바꾸지 않고 실패한다 (볼트를 잘못 읽어 글이 전부 내려가는 것을 막는다)

### 다시 발행할 때

- 내용이 같으면 내용을 다시 쓰지 않는다. 내용 해시(`contentHash`)로 비교한다. 그래서 수정 시각은 실제로 내용이 바뀐 시각이다
- 상태 변화(`UNPUBLISHED`에서 다시 발행)는 내용이 같아도 반영한다
- 처음 발행일은 바뀌지 않는다. 화면에 보이는 날짜는 발행일이다. frontmatter에 날짜가 있으면 그 날짜를 쓴다 (필드는 6. 글 속성)
- 본문의 첨부 이미지는 동기화 때 이미지 저장소로 옮기고 본문의 경로를 바꾼다. 저장소 종류는 인프라 단계에서 정한다

### 문제 있는 노트

- 다음 노트는 건너뛴다: `id`나 `slug`가 없음, slug 형식이 틀림, 다른 글이 지금 쓰거나 예전에 쓴 slug와 겹침, 같은 `id`를 가진 노트가 둘 이상
- 건너뛰어도 나머지 글은 정상으로 반영한다. 건너뛴 노트는 이유와 함께 보고한다
- 건너뛴 노트와 같은 `id`의 글이 DB에 있으면 그대로 둔다 (발행 취소하지 않는다). `id`가 없는 노트는 어느 글인지 알 수 없으므로 이 보호를 받지 못한다

## 6. 글 속성

글의 속성은 모두 옵시디언 frontmatter에서 받는다.

| 속성 | frontmatter | 규칙 |
|---|---|---|
| id | `id` | 3. 글 식별 |
| 제목 | `title` | 없거나 비어 있으면 파일 이름(확장자 제외)을 쓴다 |
| slug | `slug` | 3. 글 식별 |
| 발행 여부 | `publish` | 5. 발행 |
| 태그 | `tags` (옵시디언 기본 속성) | 카테고리는 없다. 글 하나에 여러 개 |
| 요약 | `summary` | 아래 |
| 대표 여부·순서 | 미정 | 홈 "여기부터 보세요"에 순서대로 나온다 (P1) |
| 발행일 | 미정 | 있으면 화면에 보이는 날짜로 쓴다. 없으면 처음 발행된 날 |

### 요약

- `summary`에 직접 쓴다. 비어 있으면 동기화가 본문 앞부분으로 만든다
- 직접 쓴 요약인지 자동으로 만든 요약인지 구분해 저장한다. 자동 요약 방식이 바뀌어도 직접 쓴 요약은 덮어쓰지 않는다
- 요약은 동기화 때 미리 만들어 둔다. 글 목록은 본문 없이 요약으로 보여준다

## 7. 링크

- 링크는 본문에서 다시 만드는 파생 데이터다. 동기화 때 본문의 `[[위키링크]]`와 외부 링크를 읽어 그 글의 링크를 통째로 새로 만든다
- 링크를 따로 관리하는 곳은 없다. 본문에서 지우면 링크도 사라진다
- 링크에 "왜 연결했는지" 칸은 두지 않는다
- 백링크("이 글을 언급한 글")는 도착 글 기준으로 링크를 조회한다. 이 조회를 위한 인덱스가 필요하다 (P1)

### 블로그에 없는 글로의 링크

- 위키링크는 노트 이름을 가리킨다. 동기화가 노트 이름으로 도착 글을 찾는다
- 도착 글이 아직 없거나 발행되지 않았으면(`UNPUBLISHED` 포함) 링크를 허용하고 대상 노트 이름을 저장한다. 화면에는 일반 텍스트로 보인다
- 도착 글 찾기는 매 동기화 때 모든 발행 글에 대해 다시 하고, 바뀐 연결은 저장한다. 내용이 같아 내용을 다시 쓰지 않는 글도 마찬가지다. 그래서 도착 글이 발행되면 링크를 쓴 글을 고치지 않아도 연결된다
- 저장된 대상 이름으로 "링크는 걸었지만 아직 블로그에 없는 글" 목록을 뽑을 수 있다

## 8. 글 속 데모 표시법

- 글 본문 안에서 동작하는 데모(P2)를 끼울 자리의 표시법: 미정
- 정하기 전까지 동기화는 본문의 데모 표시를 따로 해석하지 않는다

## 9. 히스토리

- 종류는 코테, 영어, 안 하기 세 가지다. P0는 코테와 영어, 안 하기는 P1이다
- 히스토리 한 줄은 항목 하나다: 코테 문제 1개, 영어 하루 결과 1건, 안 하기 실패 1건
- 같은 종류 + 날짜 + 외부 ID는 한 줄만 있다 (유니크 키). 수집이 같은 날 여러 번 돌아도 결과가 같다
  - 외부 ID: 코테는 `programmers:<문제 번호>`, 영어는 날짜, 안 하기는 항목
- 잔디 한 칸은 그날 그 종류의 줄 수로 칠한다
- 안 하기는 실패한 날만 기록한다. 기록이 없는 날은 지킨 날이다. 바빠서 체크하지 못한 날도 스트릭이 이어진다
- 수집한 기록은 DB가 보관한다. 수집은 새 기록을 더하기만 하고(영어의 같은 날 덮어쓰기는 예외), 원본(GitHub, 캡처, 수기 체크)에서 사라져도 기록은 지우지 않는다. 지워야 하면 따로 지운다
- 히스토리의 원본: 수집 전에는 각 외부 출처, 수집한 뒤에는 DB

### 코테

- 프로그래머스 문제만 기록한다. 다른 사이트(7일 7솔 스터디 사이트 등)는 기록하지 않는다
- 외부 ID는 `programmers:<문제 번호>`다 (예: `programmers:120845`). 풀이 파일 경로나 커밋은 외부 ID로 쓰지 않는다
- 같은 문제를 다른 날 다시 풀면 날짜가 달라 새 줄로 쌓인다
- 수집 경로: GitHub `2Jin1031/Algorithm` 저장소. 백준허브 확장 프로그램이 `프로그래머스/{레벨}/{번호}. {제목}/` 폴더로 올리고, 폴더마다 `README.md`에 "제출 일자"가 있다
- 문제 번호는 폴더 이름에서 뽑는다
- 기록 날짜는 커밋 시각이 아니라 README의 제출 일자다. 업로드가 늦어져도 푼 날에 칠해진다. README에 적힌 날짜를 그대로 쓴다

### 영어

- 캡처로 수집한다
- 캡처는 그날 학습을 마친 결과 화면 한 장이다. 영어 기록은 하루에 한 줄이다
- 외부 ID는 날짜다. 같은 날 캡처를 다시 올리면 그날 기록을 새 값으로 덮어쓴다 (중간 캡처와 최종 캡처가 함께 쌓이지 않게)
- 캡처는 옵시디언 노트에 이미지로 붙여 넣는다 (예: `![[Pasted image 20261014015659.png]]`)
- 수집이 영어 캡처 노트를 어떻게 찾는지(폴더, frontmatter 등): 미정
- 캡처 화면에는 날짜가 없다. "오늘"과 요일만 있다. 화면에서 읽을 수 있는 값: 하루 목표, 목표 달성률, 복습 정답률, 오늘 학습 시간, 오늘 푼 문제 수
- 기록 날짜를 어디서 얻을지(붙여 넣은 시각, 촬영 시각, 자정을 넘긴 학습의 처리): 미정
- 저장하는 값: 오늘 푼 문제 수, 오늘 학습 시간, 복습 정답률, 하루 목표, 목표 달성률
- 캡처 이미지도 이미지 저장소에 보관하고, 원래 파일 이름(붙여 넣은 시각이 들어 있다)도 남긴다. 글자 인식이 틀렸거나 날짜 규칙이 정해졌을 때 지난 기록을 다시 계산하기 위해서다
- 보관한 이미지를 화면에 보여줄지는 정하지 않는다 (화면 문제)

### 안 하기 (P1)

- 실패한 날만 기록한다. 외부 ID는 항목이다
- 안 하기 항목(예: 사과게임)은 관련 글을 가리킬 수 있다 (스트릭에서 글로 들어가는 래빗홀 입구)
- 항목을 어디에 정의하는지, 실패를 어떻게 체크하고 수집하는지: 미정

## 10. 조회 (P0)

| 화면 | 읽는 데이터 | 규칙 |
|---|---|---|
| 홈: 최근 글 | `PUBLISHED` 글 | 발행일 최신순. 본문은 읽지 않는다 (제목, 요약, 태그, 발행일) |
| 홈: 히스토리 잔디 | 코테, 영어 기록 | 종류별·날짜별 줄 수 (영어는 하루 한 줄) |
| 글 목록 | `PUBLISHED` 글 | 최근 글과 같다 |
| 글 상세 | slug로 찾은 `PUBLISHED` 글 | 옛 slug면 지금 slug의 URL로 리다이렉트한다. 본문 링크는 도착 글이 블로그에 있으면 링크, 없으면 일반 텍스트 |

- `UNPUBLISHED` 글은 어느 화면에도 나오지 않는다
- 한 줄 소개 문구, 잔디가 보여줄 기간, 화면 배치는 스펙에서 정하지 않는다

## 11. 이벤트

| 이벤트 | 언제 | 받는 쪽 후보 (참고) |
|---|---|---|
| `PostPublished` | 글이 처음 발행되거나, `UNPUBLISHED`였던 글이 다시 발행됨 | 캐시 무효화와 데우기, 백링크 갱신, 구독 알림(MVP 이후) |
| `PostRevised` | 발행된 글의 내용이 바뀜 | 캐시 무효화와 데우기, 백링크 갱신 |
| `PostUnpublished` | 글이 `UNPUBLISHED`가 됨 | 캐시 무효화, 백링크 갱신 |
| `HistoryRecorded` | 히스토리가 새로 기록되거나, 영어의 같은 날 기록이 새 값으로 바뀜 | 잔디 캐시 갱신 |

- "받는 쪽 후보"는 이벤트 이름을 정하기 위한 참고다. 이 스펙이 요구하는 구현이 아니다
- 내용도 상태도 바뀌지 않은 글은 이벤트를 내지 않는다
- 이벤트 이름은 바꾸지 않는다 (Outbox에 저장되면 데이터가 된다)
- 이벤트를 어떻게 전달하는지(Outbox, MQ)는 정하지 않는다
