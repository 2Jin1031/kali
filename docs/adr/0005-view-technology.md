# 0005. 화면 기술: Spring 서버 렌더링(Thymeleaf)

상태: 수락됨
날짜: 2026-10-13

## 상황

- 화면 요구: 잔디 칸 마우스 오버(P0), 본문 링크 요약(P1), 글 본문 안에서 동작하는 데모(P2)
- 면접관이 링크로 바로 들어오므로 첫 화면이 빨리 뜨고 검색에 잡혀야 함
- 이 블로그 자체가 백엔드 포트폴리오. 캐싱 실험은 "글 읽기 요청이 Spring을 거친다"가 전제
- 검사 명령이 하나일수록 AI가 혼자 일하기 단순

## 선택지

- (가) Spring 서버 렌더링(Thymeleaf) + 필요한 곳만 작은 JS
- (나) Next.js 별도 프론트 + Spring API
- (다) 정적 사이트 생성(Astro 등) + Spring은 동기화·로그 API만

| 기준 | (가) | (나) | (다) |
|---|---|---|---|
| 마우스 오버 (P0·P1) | ○ | ○ | ○ |
| 본문 데모 (P2) | △ 데모 JS를 따로 빌드해 끼움 | ○ | ○ |
| 첫 화면 속도·검색 노출 | ○ | ○ | ○ 가장 빠름 |
| 글 읽기가 Spring을 거침 (캐싱 실험) | ○ | △ Next 자체 캐시 | ✕ |
| 앱·배포 개수 | 1 | 2 (언어 2) | 2 |
| 검사 명령 | `gradlew` 하나 | gradlew + pnpm | gradlew + pnpm |

## 결정

(가) Spring 서버 렌더링(Thymeleaf) + 필요한 곳만 작은 JS.

## 결과

- 앱 하나, 검사 명령 `./gradlew check` 하나
- 데모는 나중에 따로 빌드한 JS 조각을 본문의 데모 자리에 끼운다. 다른 방식으로 바꿔도 도메인·DB는 그대로

## 재검토 조건

- 데모가 3개 넘게 쌓여 데모 JS 관리가 부담이 될 때
- 지원 방향에 프론트 역량 증명이 필요해질 때
